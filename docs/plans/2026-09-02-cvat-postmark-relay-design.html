CVAT-Only Postmark Relay Design

A private, queue-backed outbound email path for CVAT invitations and account messages.

2026-09-02 · CVAT fork · Approved design

Executive summary

CVAT will submit one-to-one transactional messages to a private Postfix container. Postfix will queue those messages durably and relay them to Postmark over authenticated STARTTLS. Only cvat_server will share the relay network; the relay will publish no host port and provide no inbound mailboxes.

Decision

Use a containerized, CVAT-only Postfix smarthost. Keep Postmark credentials outside Git and outside the Django container.

Context and completed prerequisites

  • Postmark account approval is complete.
  • cvat.the-commander.net is verified for DKIM and a custom Return-Path.
  • The parent DMARC policy remains p=reject and sends aggregate reports to Postmark's reporting service.
  • The root domain uses a null MX, while the website A record remains independent.
  • A dedicated transactional SMTP token has been generated and stored by the operator; no credential value belongs in this repository or document.
  • The current CVAT production settings deliberately set EMAIL_BACKEND = None.

Options considered

Selected

Compose-managed Postfix

A dedicated relay container shipped with an opt-in Compose overlay.

  • Reproducible and isolated with a persistent queue
  • Django never sees the Postmark token
  • Adds a small image and service to maintain

Host-level Postfix

Install and configure Postfix through the host operating system.

  • Independent of Compose lifecycle
  • Machine-specific configuration and rollback
  • Harder to review alongside the fork

Direct Django SMTP

Connect cvat_server directly to Postmark.

  • Fewest components
  • Credential enters the application container
  • No independent durable local queue

Architecture and trust boundaries

flowchart LR
  UI[CVAT organization UI] --> API[cvat_server]
  API -->|SMTP port 25\nprivate Docker network| RELAY[cvat_mail_relay\nPostfix]
  RELAY -->|STARTTLS port 587\nSMTP token| PM[smtp.postmarkapp.com]
  PM --> INBOX[Recipient mailbox]
  PM --> ACTIVITY[Postmark Activity\nand suppression data]
  SECRET[/root-owned host secrets/] -. read only .-> RELAY
  QUEUE[(named queue volume)] --- RELAY
  • A dedicated bridge network connects only cvat_server and cvat_mail_relay as Compose services.
  • The bridge permits outbound NAT so Postfix can reach Postmark, but no relay port is published on the host.
  • Postfix permits relay only from its trusted dedicated subnet. The Docker host remains part of the administrator trust boundary and can potentially address bridge containers directly.
  • The ordinary CVAT network and services remain unchanged; workers do not receive mail settings.
  • The Postfix queue uses a named volume so pending mail survives container replacement.

Configuration contract

Django side

EMAIL_BACKEND = django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST = cvat_mail_relay
EMAIL_PORT = 25
EMAIL_USE_TLS = false
EMAIL_USE_SSL = false
EMAIL_TIMEOUT = 10
DEFAULT_FROM_EMAIL = CVAT <no-reply@cvat.the-commander.net>

The private container hop is unauthenticated because access is enforced by network isolation. Authentication and encryption are mandatory on the Internet-facing Postfix-to-Postmark hop.

Postfix side

relayhost = [smtp.postmarkapp.com]:587
smtp_sasl_auth_enable = yes
smtp_tls_security_level = encrypt
smtpd_relay_restrictions = permit_mynetworks,reject
disable_vrfy_command = yes

The implementation plan will pin the base image, install the smallest required Postfix/SASL/CA packages, and render the private credential map only when the container starts.

Secret lifecycle

  1. The operator creates root-owned files outside the repository at /etc/cvat/secrets/postmark_smtp_access_key and /etc/cvat/secrets/postmark_smtp_secret_key.
  2. Each file uses mode 0600 and is mounted read-only under /run/secrets/.
  3. The relay entrypoint validates both values, generates an in-container SASL map with restrictive permissions, compiles it, and never prints its contents.
  4. Revocation is performed in Postmark, followed by replacing the host files and recreating only the relay container.
Credential boundary

Secrets must not appear in environment variables, Compose YAML, image layers, shell history, test fixtures, logs, screenshots or Git.

Verification strategy

Automated checks

  • Test-first coverage for settings parsing, required values, sender identity, timeout and invitation message generation.
  • Entrypoint tests for absent and empty secrets before testing successful configuration rendering.
  • Static and resolved-Compose assertions: no published SMTP port, read-only secrets, named queue volume, dedicated network membership and no credential values.
  • Image build plus postfix check without contacting Postmark.
  • Regression tests demonstrating that omitting the overlay leaves default CVAT behavior unchanged.
Baseline environment note

The first host-side baseline invocation is blocked before collection because pytest-cases and pytest-timeout are absent; the host also has Django 4.2 while the running server image has Django 5.2.14. The implementation plan must select an isolated, version-matched test environment instead of mutating the host Python installation implicitly.

Staged external checks

  1. Resolve Postmark DNS and negotiate STARTTLS on port 587 without exposing authentication data.
  2. Submit a harmless message to test@blackhole.postmarkapp.com and confirm Postmark Activity plus an empty local queue.
  3. Send to a mailbox controlled by the operator and inspect headers for spf=pass, dkim=pass and dmarc=pass.
  4. Recreate only cvat_server with the production email settings and confirm API health.
  5. Resend or create a controlled organization invitation, verify its HTTPS link, accept it, and inspect CVAT and Postmark logs.

Deployment and rollback

The tracked overlay is explicitly included in the production Compose command. It builds the relay image, attaches the dedicated network, mounts secrets, and switches only cvat_server to the production email settings module. Database, UI, workers and Nuclio functions are not recreated for this slice.

Rollback removes the email overlay from the Compose invocation and recreates cvat_server. The default settings return to EMAIL_BACKEND = None; queued relay data is retained until the operator explicitly decides whether to deliver or discard it.

Approval boundaries

Writing and verification do not authorize commit, merge, push, production restart, live invitation delivery or queue deletion. Each remains a separate operator decision.

Success criteria

  • CVAT no longer reports that no email backend is configured when the overlay is selected.
  • A real organization invitation reaches an external recipient and its acceptance link works.
  • SPF, DKIM and DMARC pass on the received message.
  • Temporary upstream failures queue rather than lose mail.
  • No SMTP port is published or bound on a host interface, and the relay is not reachable from the Internet.
  • The Postmark secret exists only in operator-controlled host storage and the running relay.
  • Omitting the overlay preserves upstream CVAT behavior.

Explicit non-goals

  • Inbound SMTP, local mailboxes, POP3 or IMAP.
  • Relay access for applications other than CVAT.
  • Newsletters, broadcasts or marketing email.
  • Mandatory account verification or changed invitation semantics.
  • Replacing Postmark's bounce, suppression or DMARC-reporting facilities.
