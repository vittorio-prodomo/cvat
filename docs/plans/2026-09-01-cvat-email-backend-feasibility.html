CVAT email backend feasibility

Why organization invitations fail today, what enabling production mail requires, and a low-risk implementation path.

2026-09-01 · Live checkout 1ba5b66b1 · Live Compose deployment inspected · Research only, not implemented

Executive summary

This is highly feasible and does not require building an email system. CVAT already creates invitation messages, renders the HTML template, generates the acceptance link, tracks send time and expiry, and calls Django's mail API. The failure is deliberate: production settings set EMAIL_BACKEND = None, and the running container confirms that no SMTP host, credentials, sender, TLS mode, or timeout has been configured.

The recommended implementation is a small, provider-neutral production settings module that enables Django's built-in SMTP backend from validated environment variables and reads the SMTP password from a Compose secret file. Only cvat_server needs the secret because the current send paths are synchronous web requests. The main work outside CVAT is obtaining an authorized SMTP relay or transactional provider, authenticating the sender domain, and testing deliverability.

Feasibility verdict

High feasibility / low application-code risk / moderate operational dependency. No database migration, UI feature, custom mail library, or worker queue is needed for the first production slice.

Important invitation behavior

The default ORG_INVITATION_CONFIRM = "No" means an existing CVAT user is added immediately without an email. A new/unregistered address receives an invitation because CVAT creates a placeholder account. If every invitee—including existing users—must receive and explicitly accept an invitation, enabling ORG_INVITATION_CONFIRM is a separate behavior decision.

Options considered

Recommended

Existing SMTP relay or transactional SMTP

Use Django's built-in SMTP backend with an institutional relay if available; otherwise use a reputable transactional provider's SMTP endpoint.

  • Smallest CVAT change
  • No new Python dependency
  • Provider-neutral and easy to test
  • Requires credentials and sender-domain work

Provider HTTP API backend

Write or install a provider-specific Django backend that calls an email API.

  • Potentially richer telemetry
  • More code, dependencies and lock-in
  • Unnecessary at current invitation volume

Self-hosted Postfix relay

Operate an MTA beside CVAT and relay mail from Django to it.

  • Full infrastructure control
  • Highest security, reputation and maintenance burden
  • Not recommended unless such an MTA already exists

Console/file backend

Render messages to logs or files for development validation.

  • Useful as a preflight smoke test
  • Does not deliver invitations
  • Not a production solution

Why a separate settings module

A new module such as cvat.settings.production_email can import all normal production settings, then add only mail configuration. This avoids turning the existing email_settings.py into a production file: that module uses the console backend and also enables mandatory account verification. It also keeps the fork-specific integration isolated from base.py, reducing future upstream-sync conflicts.

Necessary implementation steps

  1. Choose the sender and relay. Ask the institutional IT team whether an authenticated or IP-allowlisted SMTP submission service is available. If not, select a transactional provider with SMTP support. Obtain host, port, TLS mode, username/password (or relay rule), sender address, rate limits and sandbox restrictions.
  2. Authenticate the sender domain. Configure the provider-required SPF and DKIM records and publish DMARC deliberately. The public CVAT hostname and the email From domain do not need to be the same; do not assume the duckdns.org hostname is an appropriate sender identity.
  3. Add the settings module with validation. Read non-secret values from environment variables and the password from a file. Fail startup clearly for missing host/from, invalid port, unreadable secret, or simultaneous TLS and SSL.
  4. Add focused tests. Cover settings parsing, secret-file reading, TLS/SSL validation, finite timeout, and the invitation send path with Django's in-memory backend. Assert subject, recipient, HTTPS host, invitation key and sent_date.
  5. Wire only cvat_server. Add DJANGO_SETTINGS_MODULE, non-secret SMTP values and the Compose secret to the server override. Current code search shows organization invitations and password resets are sent in web-request code, not in RQ workers.
  6. Build and preflight. Rebuild the local cvat/server:dev image using the established CVAT build procedure, inspect the resolved Compose model without printing the secret, and validate DNS/TCP/TLS connectivity from a disposable server container.
  7. Send a controlled test. Use a provider sandbox or a designated test mailbox. Verify From identity, SPF/DKIM/DMARC results, the current HTML rendering, and that the link is https://cvat-unina.duckdns.org/..., not an internal host or HTTP URL. Consider adding a plain-text alternative as a separate message-quality improvement.
  8. Roll out narrowly. Recreate cvat_server; workers, database, UI and Nuclio do not need a restart for this slice. Confirm API health and logs before sending a real invitation.
  9. Recover the existing invitation. Use the UI's Resend action for the one pending unsent record after SMTP passes; do not create the same membership again.
  10. Exercise acceptance and reset. Verify new-user invitation, resend, expiry/acceptance, and optionally password reset. Decide separately whether to enable mandatory signup email verification or confirmation for existing-user invitations.

Risks and follow-on decisions

Synchronous failure behavior

SMTP happens inside the HTTP request. A slow relay delays the invitation action; authentication or network errors can return HTTP 500. Set a finite timeout and monitor errors. At the current low volume this is acceptable. A queued outbox with retry and provider bounce webhooks would be a later reliability slice, not a prerequisite.

  • Deliverability dominates calendar time. CVAT configuration is small; institutional approval, provider sandbox exit and DNS propagation may take longer.
  • Sender identity matters. Avoid webmaster@localhost and consumer-address spoofing. Use a From domain the relay is authorized to sign.
  • Invitation links are bearer credentials. They are random and expire after seven days by default; do not log message bodies or invitation keys.
  • Existing-user semantics need a conscious choice. Enabling ORG_INVITATION_CONFIRM changes membership activation behavior and should not be bundled silently with SMTP.
  • Template polish is optional. The current invitation is HTML-only and loads its logo from GitHub and web fonts from Google. A plain-text alternative and self-hosted assets can be added later for compatibility and privacy, but they do not block sending.

Indicative effort

Assuming SMTP credentials and an authorized sender are available: roughly half a development day for the settings module, tests and Compose wiring, plus one to two hours for build, rollout and browser/mailbox smoke testing. Provider onboarding, institutional approval and DNS authentication can expand the calendar time from hours to several days. Operating a new self-hosted MTA would be a materially larger project.

Recommendation

Proceed as a small, isolated hardening/configuration feature: provider-neutral SMTP settings, Compose secret, finite timeout, focused tests, and a server-only rollout. First ask the university/organization mail administrator for a TLS-capable relay and permitted sender address. If none is available, select a transactional SMTP provider and a sender domain you control. Keep ORG_INVITATION_CONFIRM and mandatory account email verification unchanged in the first slice unless you explicitly want those workflow changes.

Decision inputs needed before implementation

SMTP provider/relay, authorized From address/domain, port and TLS mode, authentication method, who can edit DNS, and whether existing CVAT users should also receive confirmation emails.
