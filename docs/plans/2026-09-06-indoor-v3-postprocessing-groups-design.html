Indoor v3 Postprocessing Compatibility Groups

Reusable model metadata for selective cross-class NMS and NMM, plus fixed two-decimal confidence attributes.

2026-09-06 · CVAT fork · Approved design

Executive summary

Indoor v3 will declare C5 and C6 as a postprocessing compatibility group in its Nuclio metadata. CVAT will resolve model-label names through the active label mapping and let the existing browser worker compare only the resulting task-label IDs. This preserves instant confidence and overlap previews while making the mechanism reusable for future model-specific defect families.

Invariant: model metadata changes partition membership only. The selected NMS/NMM method, IoU/IoS metric, overlap threshold, confidence threshold, geometry behavior, and Disabled behavior remain generic.

Options considered

Selected

Manifest-declared groups

Expose validated label-name groups through the model API and resolve them after mapping.

Benefit: reusable and compatible with live preview.

UI hard-code

Special-case the Indoor function ID and C5/C6 in React.

Cost: brittle coupling to one deployment identity.

Handler postprocessing

Suppress or merge before returning inference results.

Cost: cannot follow live UI controls and may double-process predictions.

Metadata contract

metadata:
  annotations:
    postprocessing_label_groups: '[["C5", "C6"]]'

The backend accepts a JSON array of groups. Every group must contain at least two unique model-label names; all names must exist in the function specification; and a label may occur in at most one group. Invalid declarations make the function metadata invalid instead of silently changing inference behavior.

Runtime flow

flowchart LR
  A[Indoor manifest: C5 + C6] --> B[Lambda function API]
  B --> C[MLModel metadata]
  C --> D[Resolve active label mapping]
  D --> E[Task label ID group]
  E --> F[Browser postprocessing worker]
  F --> G[NMS / NMM / greedy NMM preview]

If both labels map to one task label, ordinary class-aware partitioning already provides the desired behavior. If fewer than two distinct task labels remain mapped, CVAT omits the compatibility group for that run. If separately declared families overlap after mapping onto the project schema, CVAT coalesces them into one connected task-label group.

Algorithm semantics

SituationRequired behavior
NMSC5 and C6 compete together; the higher score survives with its original label.
Full NMMTransitive connected components may contain both classes; the highest-ranked member supplies the output label and metadata.
Greedy NMMThe highest-ranked anchor absorbs qualifying C5/C6 candidates and supplies the output label.
Equal scoresThe earlier source response wins, preserving existing deterministic ranking.
Other classesRemain partitioned by their own mapped task-label ID.
DisabledNo suppression or merge, including between C5 and C6.
Missing/invalid scorePass through and do not participate in overlap processing.

Confidence formatting

Postprocessing continues to compare the native numeric score at full precision. Before CVAT materializes annotations, any mapped model_confidence text attribute is rewritten from the valid numeric score with toFixed(2). Values therefore appear as 0.87 or 0.90, while thresholds and winner selection retain the original precision.

Verification

  • Backend tests cover valid declarations and malformed, unknown, duplicate, and overlapping groups.
  • Core tests cover metadata exposure and defensive copying.
  • Mapping tests cover renamed task labels, unmapped members, and many declared groups.
  • Postprocessor tests cover C5/C6 behavior under all three algorithms and isolation from other classes.
  • Confidence tests cover ordinary, suppressed, merged, disabled, equal-score, and invalid-score results.
