Email delivery primer for CVAT

SMTP submission, mailbox protocols, sender identity, DNS authentication, reputation, and a practical provider-selection workflow.

2026-09-01 · Companion to the CVAT email-backend feasibility report · Current provider requirements checked

The short mental model

For CVAT, “email backend” means an outbound client connection to somebody else's mail submission service. CVAT renders a message and submits it to a trusted relay. That relay—not CVAT—does Internet mail routing, queues retries, signs DKIM, handles IP reputation, contacts recipient MX servers, and usually processes bounces.

What CVAT needs

One outbound SMTP submission endpoint, TLS, an allowed sender identity, and either SMTP credentials or an IP-authorized relay.

What CVAT does not need

No inbound SMTP server, no port 25 exposed, no MX record for the CVAT host, and no POP3/IMAP account unless humans need to read replies.

SMTP versus IMAP and POP3

ProtocolPurposeTypical secure portRole in CVAT
SMTP submissionAn application or mail client hands a new message to an authorized submission agent.587 + STARTTLS, or 465 implicit TLSRequired. This is Django's outbound connection.
SMTP transferMail servers relay messages to other mail servers using DNS MX routing.25, normally with opportunistic/required TLS depending on policyHandled by the relay/provider, not CVAT.
IMAPA client reads and manages server-side folders, flags, searches and message state.993 implicit TLSNot required to send. Useful only if someone reads replies in a mailbox.
POP3A client retrieves messages from a maildrop, historically often downloading them locally.995 implicit TLSNot required and generally less useful than IMAP for a shared service mailbox.

RFC 6409 deliberately separates submission from server-to-server relay: submission normally uses port 587, while relay remains on port 25. RFC 8314 recommends encrypted submission using STARTTLS on 587 or implicit TLS on 465. IMAP's own specification explicitly says that it does not post mail.

MAIL FROM is the SMTP envelope/return path used for bounces and SPF. The visible From: header is what the user sees and what DMARC protects. They can differ, but their domains need suitable alignment.

Why legitimate mail still goes to spam

A receiver makes a probabilistic policy decision. Authentication proves which domain authorized the message; it does not prove that the message is wanted. Inbox placement combines at least:

  • Authentication: SPF, DKIM and DMARC results and alignment.
  • Infrastructure reputation: provider/IP history, forward and reverse DNS, TLS, stable HELO identity.
  • Domain reputation: age, past complaints, consistent sender identity and link domains.
  • Recipient behavior: spam complaints, deletions, replies and prior engagement.
  • List hygiene: hard-bounce rate, unknown users, stale or scraped addresses.
  • Message quality: accurate subject, sane HTML and preferably a plain-text alternative, non-deceptive display name, valid HTTPS links, and no unrelated marketing.
  • Volume shape: no sudden bursts from a new domain or IP; respect throttling and temporary SMTP failures.
No absolute guarantee

SPF/DKIM/DMARC are necessary identity controls, not an inbox-placement certificate. A perfectly authenticated message can still be spam if reputation or recipient feedback is poor. Conversely, CVAT invitations are naturally favorable traffic: low volume, transactional, user-initiated and clearly tied to an account action.

Step 1 — choose the relay and sender identity

1

Write down the workload

CVAT sends transactional invitations and password resets, probably tens rather than thousands per day. You need external delivery, an identifiable sender, seven-day invitation links, and reliable bounce visibility. You do not need newsletter tooling or a dedicated IP.

2

Choose the visible identity before the vendor

Pick a From address that recipients will trust and that the sending organization is authorized to use, such as CVAT Notifications <cvat-notify@research.example.edu>. Ideally, replies go to a monitored mailbox or support address. The website hostname cvat-unina.duckdns.org can stay in the invitation link; it does not have to be the email sender domain.

3

Ask the institution for an application relay

An institutional relay can be the cleanest path because the institution already controls its DNS, DKIM signing, reputation and policies. Ask specifically for a server/application SMTP relay or service identity—not permission to store a personal mailbox password.

Questions to send to the mail administrator
  1. Do you provide SMTP relay for a server application that sends low-volume transactional mail to external recipients?
  2. What hostname, port and TLS mode must be used?
  3. Is authentication by static source IP, SMTP username/password, client certificate, or OAuth2?
  4. Which From addresses/domains are permitted? Can a service mailbox such as cvat-notify@… be created?
  5. Will the relay add DKIM signatures and provide SPF/DMARC alignment for that From domain?
  6. Are external recipients allowed? What are rate, recipient and message-size limits?
  7. How are hard bounces, blocks and spam complaints reported or suppressed?
  8. What credential-rotation, MFA, logging, retention and data-protection rules apply?
Current UNINA-specific caution

Public UNINA material shows a transition toward Microsoft 365, OAuth2 and MFA; the student configuration published in 2025 uses smtp.office365.com:587 with STARTTLS and OAuth2, and UNINA's MFA rollout targets October 2026. Django's stock SMTP backend exposes username/password authentication, not OAuth2. Therefore, do not assume that a personal UNINA account/password is a durable application credential. Ask CSI for a service relay or service identity with an explicitly supported application-authentication method. This is an inference from the public configuration; CSI must confirm the server-use policy.

4

If no institutional relay exists, use a transactional provider

Choose a provider that supports ordinary SMTP credentials, domain verification, automatic DKIM, custom return-path alignment, bounce/complaint suppression, EU-appropriate data processing, and a sandbox/test mode. Amazon SES and Postmark are examples of the category, not automatic recommendations; they illustrate the common workflow of verifying a domain, publishing DNS records, issuing SMTP credentials and exiting a sandbox.

5

Avoid mailbox SMTP as the long-term default

Submitting through a normal Google Workspace or Microsoft 365 mailbox can work at low volume, but it couples the application to a person/service mailbox, MFA/auth policy and per-user limits. Google offers an application relay, and Microsoft supports OAuth for SMTP AUTH; both are operationally different from a simple permanent password. A dedicated application relay or transactional SMTP credential is easier to rotate and audit.

6

Do not self-host the Internet-facing MTA

Running Postfix is technically possible, but then you own port-25 egress, static IP reputation, PTR/rDNS, abuse handling, queues, retries, DKIM keys, blocklists, feedback loops and 24/7 operations. That is disproportionate for CVAT invitation volume.

1

Select a domain or subdomain you can authorize

For a third-party provider, a dedicated subdomain such as notify.example.org isolates transactional reputation and DNS records. You need administrative control of its DNS. If the From address is under unina.it, only UNINA administrators can authorize the provider and publish the required records.

2

Create the provider's domain identity

In the provider console, add the exact sending domain. The provider will generate record names and values. Copy those exact values; do not invent production SPF or DKIM records from examples.

3

Publish DKIM first

The provider usually gives one or more selector records such as selector1._domainkey.notify.example.org, often CNAMEs into provider-controlled DNS. The provider then signs each message with the corresponding private key. Selectors allow key rotation without changing the From address. Prefer 2048-bit keys where supported.

4

Configure SPF for the envelope domain

Publish exactly one SPF policy at the domain used by the return path. A provider may ask for an include: mechanism or may configure a dedicated bounce subdomain. Never create two separate v=spf1 TXT records at one name; merge authorized senders into one policy. SPF evaluation has a ten-DNS-lookup limit.

Illustrative DNS only — provider values will differ 
; DKIM — often a provider CNAME, sometimes a TXT public key
selector1._domainkey.notify.example.org. CNAME selector1.provider.example.

; SPF for an aligned custom return-path / bounce domain
bounce.notify.example.org. TXT "v=spf1 include:spf.provider.example -all"

; DMARC starts in monitoring mode
_dmarc.notify.example.org. TXT "v=DMARC1; p=none; rua=mailto:dmarc-reports@example.org"

; Provider-specific return-path routing may also require MX/CNAME records
; Use exactly what the chosen relay generates.
5

Publish DMARC in monitoring mode

Start with p=none and aggregate reports to a mailbox or report processor that can handle XML. Confirm every legitimate sender for the domain passes and aligns. After observation, move deliberately toward quarantine and eventually reject if organizational policy permits. The current DMARC standard is RFC 9989, with aggregate reporting specified separately by RFC 9990.

6

Verify alignment, not merely pass/fail

A message can show spf=pass for a provider-owned bounce domain yet fail DMARC because that domain does not align with the visible From. DKIM is often the easiest aligned path: the provider signs with d=notify.example.org. Configure a custom return path too when available so SPF also aligns.

7

Let the provider own IP/rDNS reputation

Receivers require sensible forward and reverse DNS for the sending IP. With a transactional or institutional relay, that is the relay operator's job. With self-hosting it becomes your job, including obtaining a PTR record from the IP owner—one reason not to self-host.

8

Send cross-provider tests and inspect headers

Deliver a controlled invitation to Gmail, Outlook and an institutional mailbox. Open the original headers and look for results equivalent to:

Authentication-Results: ...;
    spf=pass smtp.mailfrom=bounce.notify.example.org;
    dkim=pass header.d=notify.example.org;
    dmarc=pass header.from=notify.example.org

Also verify TLS, visible From/Reply-To, public HTTPS invitation URL, HTML rendering, and that the provider records a delivery event rather than only “accepted for queueing.” CVAT's current invitation template is HTML-only; a plain-text alternative would be a useful later improvement.

Reputation and ongoing hygiene

Google and Yahoo require at least SPF or DKIM for all senders and publish stricter requirements for bulk senders; both call for low complaint rates, valid forward/reverse DNS and RFC-compliant messages. Microsoft likewise enforces SPF, DKIM and DMARC for high-volume Outlook.com senders. CVAT's expected volume is far below those bulk thresholds, but configuring all three correctly from day one is the sensible baseline.

  • Use one stable, accurate display name and From address for CVAT transactional mail.
  • Never mix marketing content into invitations or password resets.
  • Send only as the result of an administrator's legitimate invite action.
  • Suppress hard-bouncing addresses and investigate repeated temporary failures.
  • Monitor provider delivery, bounce and complaint dashboards; CVAT currently does not ingest provider webhooks.
  • Keep spam complaints well below 0.3%; Google recommends staying below 0.1% and never reaching 0.3%.
  • Do not “warm” by manufacturing mail. At this volume, begin with genuine controlled invitations and avoid bursts.
  • Use a monitored Reply-To if recipients may reasonably need help. Transactional account invitations do not need marketing unsubscribe links.

Security implications

  • TLS is hop-by-hop, not end-to-end. It protects CVAT-to-relay transport and usually relay-to-recipient transport, but the message exists in plaintext at endpoints and mail servers.
  • The invitation URL is a bearer secret. CVAT uses a random key and a seven-day expiry. Do not include it in application logs or provider metadata beyond the message body.
  • Use a service credential. Store it as a Compose secret, scope it to sending, rotate it, and never use a personal UNINA password.
  • Prefer domain verification over single-address spoofing. A provider should sign on behalf of a domain you are authorized to use.
  • Bounces may contain personal data. Review provider retention, region, webhook security and the applicable data-processing agreement.

A practical decision sequence for this CVAT

  1. Ask CSI the eight relay questions above, emphasizing “server application,” external recipients, DKIM/DMARC alignment, and a dedicated service sender.
  2. If CSI supplies a username/password or IP-authorized TLS relay compatible with Django, use it.
  3. If CSI supplies OAuth2-only SMTP, decide between a small OAuth-capable Django backend and a transactional provider; stock Django SMTP is not enough.
  4. If CSI cannot authorize this workload, choose a transactional provider and a domain/subdomain whose DNS you control.
  5. Publish provider-generated DKIM and return-path/SPF records, then DMARC p=none with reporting.
  6. Verify provider-side domain status and test SMTP/TLS from the CVAT host before touching production settings.
  7. Configure CVAT, send controlled cross-provider invitations, inspect authentication headers, then resend the one existing pending invitation.
Likely best outcome

A CSI-managed application relay with an authorized @unina.it service address is best if available and compatible. Otherwise, a transactional SMTP provider plus a domain/subdomain you control is technically straightforward and avoids coupling CVAT to a personal mailbox or Microsoft/Google user-auth lifecycle.
